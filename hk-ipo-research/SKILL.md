# 港股 IPO 研究

把本 skill 当作数据工具和研究流程使用，不要仅凭模型记忆回答实时问题。默认用中文输出，并注明数据时间（Asia/Hong_Kong）。所有结论仅供研究，不构成投资建议。

## 首次运行

从 skill 根目录执行：

```bash
python3 -m pip install -r scripts/requirements.txt
python3 scripts/hkipo.py --help
```

若环境不允许安装依赖，仍可使用可运行的子命令；如实报告缺少的依赖，不要静默改用臆测数据。

## 选择工作流

- 用户问“最近/今天有什么新股”：运行 `overview` 和 `tradesmart tracker`，再用港交所文件核验招股条款。
- 用户问单只 IPO：运行 `analyze <代码>`；按需补充孖展、基石、评级、保荐人和 A+H 数据。
- 用户问暗盘或上市表现：运行对应 `grey-*`、`placing` 或 `allotment` 命令；区分尚未发生与已经发生的结果。
- 用户问保荐人战绩：优先运行 `sentiment sponsor-search`，再用 `jisilu list --sponsor` 或 `etnet search` 交叉验证。
- 用户问“值不值得打/给评级”：先抓数据，再按 `references/scoring.md` 评分；不要把抓取脚本的原始输出直接当投资结论。
- 用户问指定历史日期：使用当时可获得或存档的数据，不把最终配售、暗盘或首日结果泄漏到事前判断；如需复盘，把预测与结果分栏。
- 用户要求每日自动研究并推送 RSS：运行 `scripts/daily_rss_report.py`。它先按 `stock-info-dingding` 的新浪 IPO 列表逻辑发现今天仍在招股的 code，再逐只运行 `hkipo.py analyze`，最后生成或推送 Markdown。
- RSS 最终报告按 `references/report-contract.md` 检查。采集骨架不等于分析报告；先由 agent 尽量补齐财务、基石、保荐人、股东、估值和风险，再运行 `scripts/push_rss.py`。质量问题默认只告警，不阻断个人 RSS 推送。
- 当天有 N 只仍可申购的新股时，按 code 循环研究并生成 N 份 Markdown，推送 N 篇 RSS。不要合并成一篇；没有新股则不推送。

## 每日 RSS / cron path（15 分钟预算）

被 cron 触发时（无用户在场），按以下分支走：

1. **候选发现必须且只能用 `python3 scripts/daily_rss_report.py`**（新浪 `hk_IPOList.php` 源，按 `subscription_start <= today <= subscription_end and listing_date > today` 严格过滤）。命令：
   ```bash
   python3 scripts/daily_rss_report.py --date <today> --output /tmp/hk-ipo-discovery.md
   ```
   解析输出里的「今天确认有 **N 只**仍在招股」：
   - N = 0（或正文是「今天没有从新浪港股 IPO 列表确认到仍在招股的新股」）→ **直接返回 `[SILENT]`**，不推送任何文章。
   - N ≥ 1 → 拿这 N 只的 code 进入第 2 步。

   ⚠️ **禁止用 `hkipo.py overview` 或 `hkex active` 做"今天是否还有可申购"的判定**。这两个源不识别"招股已截止但尚未上市"：
   - `overview`（TradeSmart）：孖展累计数据在招股截止后仍长期展示，会被误判为"在招股"。
   - `hkex active`：状态"处理中"覆盖递表到上市的整段流程，含已截止未上市的票。
   - 历史教训：2026-08-04/05/06 拿森科技（02261.HK）招股期 7/30–8/4 已截止，但因 overview 仍显示孖展、HKEX 状态仍"处理中"，被误推 3 篇 RSS。

   `overview` / `hkex active` 只能在第 2 步及之后作为**字段补全源**使用（看孖展热度、核 HKEX 公告），不能用来判定"今天还能不能打"。

   💡 **结构层兜底**：`scripts/hkipo.py analyze <CODE>` 输出的 `subscription.subscription_close` 字段直接来自 TradeSmart（招股期截止后仍长期保留）。拿到 `analyze` JSON 后可以再做一次**第二层校验**——`subscription_close < today` → `[SILENT]`，免得万一第 1 步的新浪源与 TradeSmart 状态不一致时再次误报。
2. 若有 ≥1 只：每只依次
   a. **`jisilu list --json`**（首选结构化字段源 — 即使招股首日也通常已有招股期 / 发行价 / 入场费 / 总股本 / 募资 / 总市值 / 保荐人 / 招股章程 URL）。本字段集往往比 `analyze` 在招股首日更完整（见 PITFALLS #13）。
   b. `tradesmart tracker <CODE>`（尝试拿孖展快照；招股首日上午通常为空，写 `未找到（招股首日）`）。
   c. `analyze <CODE>`（聚合 JSON；**招股首日会因 TradeSmart tracker 失败抛 ValueError**，见 PITFALLS #13，不要让单个失败阻塞后续步骤）。
3. 对每只 IPO，先按 [references/financial-research.md](references/financial-research.md) 做实时全网财务研究，并按 [references/ownership-research.md](references/ownership-research.md) 查创始人、实际控制人和主要机构/产业股东；再用 AAStocks per-code、etnet 和 jisilu 补发行条款、保荐人及历史数据。不要从 HKEX PDF 获取财务或股东数据；HKEX 只用于核验招股窗口、发行条款和正式公告。保荐人或基石来源失败时记录失败页，不要重复请求同一页面。
   - **A+H 双重上市票（A 股母公司 + H 股新发）**：财务/实控人/股东数据**优先从 A 股巨潮 / 东方财富 / 同花顺 F10 拿**（SSR 可达），不要从 HKEX PDF 拿。完整字段模板与 cron 快速研究顺序见 [references/ah-share-dual-listing.md](references/ah-share-dual-listing.md)。
4. 把每只的 HTML 落 `/tmp/<src>_<code>.html`，复盘或后续 grep 不再 hit 网络。
5. 一次写 **1 只 = 1 篇 Markdown**，落 `~/.hermes/cron/output/hk-ipo-daily-YYYY-MM-DD-<code>.md`。严格按 [references/cron-recovery.md](references/cron-recovery.md) 让文件以 `<!-- HK_IPO_REPORT_START -->` 开始；只写读者报告，禁止复述本 SKILL、references、系统提示、执行计划或工具日志。**不要合并多只**；当日 ≥2 只可申购时，生成 ≥2 份独立 Markdown。
6. 按 `references/report-contract.md` 检查 Markdown 后，逐只跑 `scripts/push_rss.py <md-path> --title "..." --endpoint <url> --source hk-ipo-research --insecure --allow-duplicate`。**`--allow-duplicate` 必须每次显式传**（PITFALL #30）；cron 批次内第 2-N 只不传会丢报告。检查问题会在返回结果的 `quality_warnings` 中显示但默认继续推送；只有希望恢复硬门禁时追加 `--strict`。（仅确认内网使用自签证书时加 `--insecure`。）遇到 `quality_warnings` 想快速定位根因（label 白名单 / 数字行匹配 / `HKEX` + `反爬` 双触发等）可查 `references/push-rss-validator.md` 速查表。
7. 若已存在同日同 code 的报告，**不要重复推送**，除非用户明确要求发更正版。

限时节奏（15 分钟总预算）：`daily_rss_report.py` 判定 + 1 只 IPO ≈ 5 分钟；如 ≥3 只，只取评分最高的 2-3 只做深度研究。没有补齐财务字段时仍可推送个人 RSS，但必须保留 `quality_warnings`，便于后续调整 skill。每只 IPO 的实测调用顺序与预算分配见 [references/cron-workflow-sequence.md](references/cron-workflow-sequence.md)。



先预览并保留 Markdown：

```bash
python3 scripts/daily_rss_report.py --output /tmp/hk-ipo-daily.md
```

核验股票代码并完成逐股研究后，推送最终 Markdown：

```bash
python3 scripts/push_rss.py /tmp/hk-ipo-final.md \
  --title "YYYY-MM-DD 港股打新｜公司名（00000.HK）｜66分 B" \
  --endpoint https://web.duomi77.cn:9443/rss/api/rss-relay/post \
  --source hk-ipo-research \
  --insecure
```

若且仅若用户确认该内网 Relay 使用可信的自签名证书，追加 `--insecure`。不要全局关闭 TLS 校验。

不得因为单一数据源失败而跳过研究。财务数据按实时全网搜索流程取得，不依赖 HKEX PDF；港交所文件只核验发行条款和公告。收入或净利润/亏损仍为 `未找到` 时在 RSS 返回值中告警，但默认继续推送。除非用户明确要求，不要重复推送同一天的报告。

`hkipo.py analyze` 使用 TradeSmart 回填孖展总额、预计超购、申购金额和观测时间。脚本不提供财务及股东基本面；agent 必须分别按 [references/financial-research.md](references/financial-research.md) 和 [references/ownership-research.md](references/ownership-research.md) 实时搜索并交叉验证。港交所文件不作为财务或股东默认数据源。

## 命令入口（命令实际行为 — 名字不一定能猜到）

所有命令均从 skill 根目录运行。

| 命令 | 实际行为 | 不要这样用 |
|---|---|---|
| `overview` | TradeSmart 当前正在招股的 IPO 孖展 概览（aggregate JSON + plain text）| — |
| `analyze <CODE>` | 拉取 TradeSmart 孖展 + 订阅窗口 + 入场费聚合 JSON；不做基本面研究 | — |
| `tradesmart tracker [CODE]` | **实时孖展总额/超购倍数 + 观测时间** — 这是拿到孖展数据的正确入口 | — |
| `tradesmart list --json` | 返回 TradeSmart 的**入场费阶梯表**（每手数对应金额），**不是活跃 IPO 列表** | 不要拿来发现新 IPO |
| `tradesmart detail 公司简称` | 按名称精确查找 IPO；传短中文名会 `未找到`，用 `tracker <code>` 替代 | 不要靠中文名短串 |
| `hkex active` | 港交所「处理中」申请者清单；代码通常为 `null`，要按 docID/名称对照 | — |
| `futu list` | 富途历史 IPO 数据 | — |
| `jisilu list [--sponsor <X>]` | 历史港股 IPO + 保荐人过滤；这是**保荐人战绩**推荐入口 | — |
| `sentiment sponsor-search --name <X>` | ⚠️ 当前**不会做模糊匹配**，传部分中文通常 `未找到`；用 `jisilu list --sponsor` 替代 | 不要靠此命令找保荐人 |
| `etnet search / list` | ⚠️ 当前可能报 `ImportError`，网页也可能 403 | 不要反复 curl；基本面直接走实时网页搜索，保荐人改用 jisilu |
| `odds --oversub <X> --price <Y>` | 中签率预测计算器 | — |

```bash
python3 scripts/hkipo.py overview
python3 scripts/hkipo.py analyze 02692
python3 scripts/hkipo.py tradesmart tracker
python3 scripts/hkipo.py tradesmart tracker 02692

python3 scripts/hkipo.py hkex active
python3 scripts/hkipo.py futu list
python3 scripts/hkipo.py jisilu list --sponsor 招商
python3 scripts/hkipo.py sentiment sponsor-search --name 招商
python3 scripts/hkipo.py odds --oversub 38 --price 73
python3 scripts/hkipo.py tradesmart tracker 02261
```

## PITFALLS（save these — they cost time every run）

1. **`tradesmart list ≠ active IPOs`.** 返回的是入场费表。看到输出包含 "公发 / 最低档" 时立刻意识到这是阶梯表，不是新股票列表。要看活跃 IPO 用 `tradesmart tracker`。
2. **HKEX 招股书 PDF 链接（`.../sehk/YYYY/.../sehkYYMMDDxxxxx_c.pdf`）从 CLI/curl 抓不到**，返回约 2 KB 错误 HTML。财务数据不要再请求该 PDF；立即按 `references/financial-research.md` 用公司名、代码和财务关键词做实时全网研究。HKEX 仅用于发行条款与公告核验。
3. **AAStocks per-code 只作为发行条款的可选来源**，不是财务/股东主源。URL：`https://www.aastocks.com/tc/stocks/market/ipo/upcomingipo/company-summary?symbol=<5位CODE>`。超时就跳过；不要阻塞实时全网研究。`tblMargin` 与 `tblInvestor` 常为空 placeholder，转用 TradeSmart / jisilu 或其他公开来源。
4. **保荐人 labeling 在不同来源之间不一致**（典型：`海通國際資本` / `中銀國際亞洲` vs jisilu 的 `国泰海通`）。这是合并集团 vs 单个 entity 口径差异，不是真冲突。报告里**两者都列**，写明这是"不同口径"，不要擅自统一。
5. **etnet 的 `cornerstone` / `financial` / `majorsharesholder` tab 在 HTML 里通常是空白**。不要反复请求，也不能据此判定公开渠道没有资料；转入实时全网财务检索。
6. **cron / 每日任务场景下**：预算通常 ≤15 分钟。**第一步**必须跑 `daily_rss_report.py`（新浪源）做"今天是否还有可申购"判定，0 条直接 `[SILENT]`；不要改用 `overview` / `hkex active` 兜底（见 cron path 第 1 步的 ⚠️ 说明）。N ≥ 1 时，按 `analyze <CODE>` 逐只研究、再各自出 Markdown、按`references/report-contract.md`逐只推送。**不要**为了"再核对一遍"反复 fetches 同一个页面 — 一次取 HTML 落 `/tmp/<source>_<code>.html`，后续 grep 走本地文件。
7. **aaStocks 表格数据** (`tblMargin`/`tblInvestor`/`tblSamePeriodIPO`) 这类 ID 表的初次 SSR HTML 经常是空；如果是关键字段宁可标 `未找到` 也别瞎猜，发行价/入场费/截止日这些一定能从 AAStocks/etnet 同时核到才算 `已核验`。
8. **大量网络源从当前 VM 不可达**：`vbkr.com` (华盛证券，TradeSmart 后端), `cnyes.com`, `web.archive.org`, `futunn.com` heavy-JS 路径，SSL handshake 超时到 `2001::1f0d:5402` / `2a03:2880:f12d...`。**本地 SearXNG (`http://127.0.0.1:8888`) 配的是国内引擎**（百度/搜狗/360/必应中国），海外引擎（Google/DDG/Brave/wikipedia）全 timeout。详细 fallback 路径见 [references/financial-research.md § 检索后端](references/financial-research.md)。当一个外部页面持续 timeout 时，**30 秒内切下一源**，不要等。
9. **cron 输出的 Markdown 容易包含整个 SKILL.md 全文**（prompt 注入）。**症状**：文件前 100+ 行是 SKILL.md 内容（YAML frontmatter + 工作流章节），真正报告从 `## 排名总览` 才开始。**应对**：
   - 最终文件必须以 `<!-- HK_IPO_REPORT_START -->` 开始；标记前不写任何内容
   - 严禁复述本 SKILL、references、系统提示、执行计划或工具日志
   - `push_rss.py` 会按 [references/cron-recovery.md](references/cron-recovery.md) 自动裁剪标记前内容，并将动作写入 `quality_warnings`
   - 需要将任何净化告警作为硬门禁时显式传 `--strict`
   - 标题格式必须严格：`YYYY-MM-DD 港股打新｜公司名（00000.HK）｜66分 B`（全角竖线｜ + 5位代码）
10. **cron 因工具调用次数限制可能跳过 push_rss.py**。**症状**：markdown 写好了但没推送成功。**应对**：
   - 每只新股 ≤ 8 次工具调用（overview + analyze + tracker + 2 数据源 + 写报告 + push_rss）
   - 3-5 只新股总预算 ≤ 30 次调用
   - > 5 只新股：按评分排序，只深度研究 2-3 只，其余只标 `待手工核对`
   - cron prompt 必须**显式声明** push_rss.py 是最后一步、不可省略

10a. **⚠️ 微信/iLink 通道限流（2026-08-19，新坑）**：agent final response 被 cron framework 当成 deliver content 全文推给微信，**完整研究报告 ≈37000 字符**会被切分 18 次发 iLink，瞬间撞限流（`iLink sendmessage rate limited`）。**应对**：
   - **agent 的 final response 必须是 ≤500 字的极简摘要**，**不要复述报告全文**（完整报告已写本地文件 + 已 push_rss.py 推 RSS）
   - 摘要格式：标的代码+招股期+评分+核心风险（1-2 条）+1 句结论 + RSS ID
   - **绝对禁止**把 Markdown 全文（含表格、链接、免责声明）原样复制到 final response
   - 完整报告路径写在摘要末尾一句话：`完整报告已存 ~/.hermes/cron/output/hk-ipo-daily-YYYY-MM-DD-CODE.md，RSS 已推 ID XXXXX`
   - 用户从微信读摘要即可，要看详细报告去飞书云文档 / RSS

10b. **⚠️ iLink 服务端 chat_id 限流（2026-08-20，新坑）**：PITFALL 10a 修了之后 agent final response 已压到 600 字（远低于 2000 字符 MAX_MESSAGE_LENGTH），**但 iLink 服务端仍然返回 `sendmessage rate limited`**。**真凶是 iLink 服务端对具体 chat_id（如 `o9cq80y4`）标记的"send too often"，不是 Hermes 本地 circuit breaker 问题**。**应对**：
   - **不要**继续调 `.env` 里的 `WEIXIN_RATE_LIMIT_CIRCUIT_THRESHOLD` / `OPEN_SECONDS` / `CHUNK_RETRY_DELAY` —— 这些只改 Hermes 本地 circuit breaker，**iLink 服务端限流不受其影响**
   - **诊断方法**：看 `~/.hermes/logs/gateway.log`，如果连续出现 `[Weixin] rate limited for o9cq80y4; backing off 6.0s before retry`（backoff 间隔固定 6s，最终 cooldown 60s），**且 chat_id 一直是同一个**，就是 iLink 服务端限流
   - **iLink 服务端限流信号**：gateway.log 里**该 chat_id 没有任何成功 send 记录**（grep `messageId` 或 `sent` 拿不到该 chat_id 历史）
   - **iLink 服务端限流时长**：未知，可能几小时~几天，无自动解封时间表
   - **应对方案**（按优先级）：
     1. **保持现状，等 iLink 自动解封**（RSS 推送仍正常工作，微信只是次要通道）
     2. 临时改 cron deliver = `local`（只存文件，不发任何通道），避免失败累加污染 cron state
     3. 联系微信开放平台客服申请解除
     4. 切换 home channel 到新 chat_id（需用户重新配对，影响大）
   - **不要**为这个问题继续修改 SKILL 或 .env —— iLink 服务端限流与 SKILL/.env 无关，**改 SKILL 是错方向**
11. **TradeSmart `observed_at` 是当前抓取时刻，不是历史时刻**。当目标 IPO 已截止招股、已定价或已上市时，TradeSmart 仍展示孖展数据，但 `observed_at` 时间戳对应"截止日后的最终孖展快照"，晚于任何"招股截止前"的预测截止点。**判定规则**：`observed_at` ≤ 截止点 → 可用并标注时间戳；`observed_at` > 截止点 → **未来数据，不得用于方向判断**；TradeSmart 没有时间回溯 API，做回测时若本地无截止点前的快照存档，孖展具体数值不可证，只能承认定性热度结论（"招股期热度持续极热"），从打分中剔除并在报告中显式标注 `时间不可证`。
12. **`jisilu list --json` 是候选全集重建的最佳入口**（回测场景）。按 `apply_date ≤ cutoff ≤ apply_end_date` 过滤即得截止点仍处招股窗口的全部候选，不依赖 TradeSmart 实时状态（TradeSmart 招股截止后仍长期保留孖展数据，会被误判）。**`futu list` 的 `listing_date` 是 `1970-01-21` 占位符**，不能用作 listing_date 来源；必须用 jisilu / 港交所招股章程交叉验证。
13. **`analyze <CODE>` 在招股首日会因 TradeSmart tracker 失败而抛 `ValueError: IPO Tracker 页面未找到孖展嵌入数据`**（典型首日 8/17 上午）。`analyze` 内部依赖 `get_tracker_margin()` → `fetch_tracker_margin_records()`，首日孖展快照尚未生成就拿不到。
   - **不要**让单个 ValueError 中断后续研究流 — `analyze` 输出只是元数据聚合，关键字段已能从 `jisilu list --json` 拿到（招股期、价格、入场费、总股本、募资、市值、保荐人、招股章程 URL 全部在内）。

15. **`curl … | python3 -c '…'` 被 tirith 安全钩拒绝**。当前 VM 的 `tirith` 拦截 "Pipe to interpreter: download content will be executed without inspection" 模式，常见错误信息：`[HIGH] Pipe to interpreter: curl | python3: Command pipes output from 'curl' directly to interpreter 'python3'`。**应对**：
   - 把 HTML 先落本地再处理：`curl -sL --max-time N URL > /tmp/foo.html`，然后用 `read_file` / `search_files` 处理本地文件。
   - 用 `execute_code` 配合 `web_fetch` / `requests`（execute_code 在受信任执行环境内不触发 tirith）。
   - 用 `web_extract(urls=[URL])` 工具直接吃页面，绕开 shell pipe。
   - 用 `tirith run URL` 或 `vet URL`（getvet.sh）作为受信任检查入口。
   - **不要**反复 retry 同一 `curl | python3` 命令浪费时间。

15a. **`web_extract` 当前 backend 不可用（2026-09-17 新坑，SearXNG 仅搜索）**。实测本批 2 次 `web_extract(urls=[...])` 均返回 `{"success": false, "error": "SearXNG is a search-only backend and cannot extract URL content. Set web.extract_backend to firecrawl, tavily, exa, or parallel."}`——本地 SearXNG 仅配置搜索后端，没有抽取能力。

     1. **不要 retry `web_extract`**——同样的错误会持续返回

16. **`push_rss.py` 章节检查是子串匹配、不是 fuzzy match**。实测 2026-08-18 推送 03223 时，正文同时包含 `## 1. 关键 Offer Terms`、`## 2. 热度`、`## 3. 财务基本面`、`## 4. 业务与股东`、`## 5. 评分`、`## 8. 数据来源` 等带编号前缀的章节，但 `push_rss.py` 返回的 `quality_warnings` 仍把六个章节全部列为"缺少章节"。原因是 checker 严格匹配 `## 关键 Offer Terms`、`## 热度` 等不带前缀的字符串，对 `## N. ` 前缀视作不命中。
   - **应对**：写最终 Markdown 时，二级标题**不要加编号前缀**，直接写 `## 关键 Offer Terms`、`## 热度`、`## 财务基本面`、`## 业务与股东`、`## 评分`、`## 建议`、`## 风险提示`、`## 数据来源`。表头 / 子节标题用三级或四级编号（如 `### 阶段 1：…`）即可保留层次。
   - 这是**误报**：`quality_warnings` 不影响 `pushed == true`，无 `--strict` 时不阻断推送；同一天不要因为这条误报重推。

17. **"业务与股东"章节的实控人字段必须落到数字或显式 `未披露`**。实测 2026-08-19 推 03223 时，正文写"控股股东 / 实际控制人为创始人 **刘强**（持股比例 A 股披露口径，需查招股书 / Wind）"，`push_rss.py` 仍返回 `quality_warnings: 业务与股东缺少创始人/实际控制人/控股股东的有效结论`。根因：contract 要求"创始人/实际控制人应给出姓名**或有来源的'无单一实际控制人'结论**"——给姓名但不给数字或显式 `未披露（已核验：来源 A、B、C）` 会被判为缺结论。
   - **应对**：写"业务与股东"章节时，对实控人字段三选一明确落地：

24. **⚠️ A+H 双重上市票的 H 股估值溢价风险（跨市场 PE 倒挂）**。A 股母公司（H 股新发前的存量上市公司）赴港二次上市的票（如 09976 江波龙 301308.SZ → 09976.HK），**H 股招股价对应 PE 经常显著高于 A 股同行业 PE**，是评级与"建议"段必须显式落地的风险点。
    - **症状**：江波龙 09976 按 2025A 归母净利 14.23 亿元 + 招股价 240.60 × 总股本 4.55 亿 = 1094.73 亿港元市值 → **H 股 PE ≈ 76.9x**，远高于半导体存储行业均值（约 30-40x）；同时 H 股较 A 股可能存在显著溢价。
    - **应对**：
      1. **反推 H 股 PE**：从 A 股年报拿最新净利 + jisilu 拿总股本 → 反推 H 股招股价 PE（A 股年报数据可从巨潮 / 东方财富 / 同花顺 F10 SSR 拿，详见 `references/ah-share-dual-listing.md`）
      2. 对比 A 股实时 PE（用 `hq.sinajs.cn` 或雪球拉）+ 行业 PE（券商研报）
      3. 风险调整：**H 股 PE > A 股 PE × 1.5** → -7~-10；**> 2x** → -12~-15（接近一票否决）
      4. 报告里在"风险提示"段单列：`H 股 PE 76.9x vs A 股 PE Xx vs 行业均值 Yy，建议仅打新博弈首日，长持需警惕向 A 股折价收敛`
    - **历史验证**：2026-09-03 江波龙 09976 H 股 PE 76.9x 偏高，按 PITFALL #24 风险调整 -7，评分从 67 降至 60 B 级。详细复盘见 `references/2026-09-03-batch-lessons.md`。

25. **⚠️ 高单价 / 高入场费 IPO 对散户的资金占用（"高单价票"陷阱）**。招股价 >100 港元 / 入场费 >10,000 港元的票（典型如 09976 江波龙 240.60 港元 / 入场费 12,030 港元）对散户本金机会成本极高。
    - **症状**：散户本金 <50 万港元时，打 1 手即占用 2.4% 资金；上 9x 孖展即占用 21.6%——一旦破发本金损失放大。
    - **应对**：
      1. 报告"建议"段必须写资金占用提示：`入场费 X 港元，占 50 万本金 Y%`
      2. 评分风险调整**额外 -3**（高单价 + 高热度组合 = 散户追高风险）
      3. 默认建议：**仅现金申购，不上孖展**
    - **历史验证**：2026-09-03 江波龙 09976 入场费 12,030 港元（约 50 万本金 2.4%），报告建议"现金 1-2 手小仓，不上孖展"，触发 PITFALL #25 风险调整 -3。

26. **⚠️ 证监会备案阶段质询是 H 股 IPO 早期风险预警（"备案六问"信号）**。H 股 IPO 在证监会境外发行备案阶段，监管可能就**股权代持 / 数据安全 / 实控人认定 / 关联交易**等关键问题发布多问质询（典型如 03231 优地机器人 2025-12-15 收到六问）。
    - **症状**：招股书聆讯通过 ≠ 监管无虞；备案质询问题可能在招股定价 / 基石引入 / 首日表现上反复发酵。
    - **应对**：
      1. web_search `"<公司名>" 证监会 备案 质询 OR 问询` 检索是否有备案阶段质询
      2. 质询问题包含 **股权代持 / 数据安全 / 实控人认定 / 关联交易** → 评分风险调整**额外 -5~-8**
      3. 报告"风险提示"段单列：备案质询问题清单 + 公开应对状态（已答复 / 仍待回复）
    - **历史验证**：2026-09-03 优地机器人 03231 备案六问（股权代持 / 数据安全 / 阿里系股东），按 PITFALL #26 风险调整额外 -8，叠加 PITFALL #27 联合创始人控股弱化 -3 + 累计亏损 -12 + 未盈利 -8，最终评分 37 C 级。

27. **⚠️ 多名联合创始人 + 一致行动人协议的实控人结构 = 单一实控人稳定性弱化**。公司由 3-5 名联合创始人共同控制 + 签订一致行动人协议（典型如 03231 优地机器人 卢鹰 + 顾震江 + 刘大志 + 罗沛 + 夏舸 5 人合计控股 33.4%）。
    - **症状**：单一实控人缺失；任一创始人退出或分歧都可能动摇公司治理与决策连续性。一致行动人协议虽提供法律约束，但执行摩擦大于单一实控人模式。
    - **应对**：
      1. web_search 找"实控人 + 一致行动人 + 合计持股"组合查询
      2. 报告里写**"无单一实控人（X 名联合创始人一致行动合计控股 Y%）"**（命中 PITFALL #17 第 2 条 `无单一实控人（来源：…）` 模板）
      3. 评分：实控人稳定性弱化 → **护城河分 -2~-3**
    - **历史验证**：2026-09-03 优地机器人 03231 5 名联合创始人合计控股 33.4%，按 PITFALL #27 护城河分 -3，最终护城河分 8/15。

28. **⚠️ 招股历史价格 vs 当前价格混叠（"earlier draft 误判为 current"，2026-09-14 新坑）**。web_search 港股 IPO 招股价时，返回的 snippet 经常同时包含：
    - **当前招股期的官方价格**（如 09856 纳真科技 32.96 港元，9/14 早间港交所披露易公告）
    - **早期招股书草稿的旧价格区间**（如 09856 在 2026-03 第二次递表时的"16.00-17.42 港元"，已被官方定价覆盖）
    - **完全无关 IPO 的同名 / 相似搜索词价格**（如搜索"09856 招股价"返回的第一条是"09615 梅卡曼德 95.30-101.70 港元"——搜索引擎把 09856 / 09615 误聚合）
    - **症状**：模型容易把 snippet 第一条 / 最高排名 / 醒目数字当成 current price；旧价格区间（95–101 或 16–17）出现在权威媒体旧标题里时尤其容易被误采。
    - **应对**：
      1. **官方定价公告时点优先**：HKEX 披露易 / 港交所招股公告 / 招股说明书附录 > 一切旧报道。当前 IPO 公告日期 ≥ 招股期开始日 → 公告时点 ≤ 招股期开始日的报道一律视为旧版。
      2. **搜索 query 必须包含公司名 + 当前月份 + "招股" + "港元"**（如 `"纳真科技" 9月14日 2026 招股价 港元`），过滤掉旧月份（"3月"、"5月"等）的报道。
      3. **价格区间 vs 单一价**：HKEX 招股公告若用"每股发售价"+"每手 X 股"句式 → 单一价（如 09856 的 32.96 港元）；若用"招股价区间"+"介乎 A 港元至 B 港元" → 区间价（如 06727 的 49–61 港元）。**两者写法不能混用**，混用即表示源数据错误。
      4. **第三方（jisilu / daily_rss_report.py）的 `price_range` 字段不可信**：09856 jisilu 显示 `"32.96-32.96"`（单一价），而 06727 显示 `"49-61"`（区间）；当 jisilu 与 HKEX 官方公告冲突时，**以 HKEX 公告为准**（jisilu 是事后回填，存在更新延迟）。
      5. **HKEX announcement PDF 反爬（CORS / 404）抓不到正文**（PITFALL #2），所以 official 定价只能用 web_search 拿；**必须从标题 / 来源 URL 二次核验公司名匹配**（不能用 09856 的搜索结果套到 09615 上）。
    - **历史验证**：2026-09-14 web_search 09856 第一波返回的"95.30-101.70 港元"实际是 09615 梅卡曼德的价格（搜索引擎聚合），"16.00-17.42 港元"是 09856 在 2026-03 第二次递表时的旧区间（已被覆盖），"32.96 港元"才是 9/14 官方公告的 current price。三者中只有"32.96"是正确的。

29. **⚠️ A+H 二次上市票的 H 股定价区间下限 / 入场费 / 每手可能在招股首日未公开（2026-09-14 新坑）**。A+H 双重上市的票（如 06700 四方精创 300468.SZ → 06700.HK）在招股首日，HKEX 招股公告常常只披露**最高发售价 / 上限**（如"不高于每股 16.00 港元"），区间下限、每手股数、入场费均未在公开媒体明确披露。
    - **症状**：A+H 票招股首日报告里，"每手股数"、"入场费"、"招股价区间下限"三字段常常只能填"未在公开媒体披露"或临时估算值。
    - **应对**：
      1. **入场费临时估算公式**：`入场费 ≈ 招股价 × 每手股数`；每手股数按 H 股惯例 100 / 200 股中常见值估（金融 IT / 银行 IT 票多用 100 股或 200 股）。
      2. **明确标注"未在公开媒体披露"**：报告里写"每手 / 入场费 / 区间下限暂缺（已核验：360kuai / jrj.com.cn / 新浪财经 / 智通财经 / 财联社）"，避免编造数字。
      3. **AAStocks per-code 兜底**：`https://www.aastocks.com/tc/stocks/market/ipo/upcomingipo/company-summary?symbol=<5位CODE>` 抓入场费表（即便 SSR HTML 经常为空，可仍尝试一次）。
      4. **不影响评分**：把"数据置信度 -2~-3"写进评分，但**报告仍可推送**——只需保留 `quality_warnings: 财务基本面 ...` 即可。
      5. **招股期推进后字段逐步可获**：06700（招股首日 9/14）三字段暂缺 vs 06727（招股倒数第二日 9/14）三字段三源核验通过 → 招股期每推进 1–2 天，公开媒体覆盖率显著提升。
    - **历史验证**：2026-09-14 06700 四方精创 + 09856 纳真科技均为招股首日报告，每手 / 入场费 / 区间下限均暂缺；06727 星环科技（招股倒数第二日）三字段已三源核验。

30. **⚠️ `push_rss.py` 按 title 字符串去重，cron 批次内第 2-N 只可能命中 `duplicate: true`（2026-09-15 新坑）**。实测 2026-09-15 推送同一 cron 批次 3 只新股时，第一只 06700 推送成功 `pushed: true`、第二只 09856 / 第三只 06727 立即返回 `{"pushed": false, "duplicate": true, "title": "..."}`。

31. **⚠️ `jisilu + analyze` 不会挖出"招股书摘要 + 财报数字"之外的重大负面信号（2026-09-15 实战新坑）**。06727 星环科技 9/15 报告评分 36/D 用了 PITFALL #18/#19/#24/#27 等全部规则，但**漏掉 6 类重大负面**，因为 `jisilu list` / `analyze` / A 股年报查询路径都**不会**主动挖这些。必须额外 web_search 关键词才能挖出。
   - **症状**：9/15 06727 报告漏掉的负面清单（用户问"新环 HR 事件"才挖出来）：
     1. **连亏 8 年**（2018-2025 累计亏损数远超报告里"2023/2024 亏 6.3 亿"）—— 新浪财经 2026-07-23
     2. **围标串标指控**（招投标违规历史）—— 新浪财经 2026-07-23
     3. **A+H 信披打架**（A 股招股书与 H 股招股书数字不一致）—— 新浪财经 2026-07-23
     4. **腾讯系减持套现 3 亿+**（战投退出）—— 新浪财经 2026-07-23
     5. **招股书首次失效**（2025-08 递表 → 2026-02 失效 → 二次递表才成功）—— 网易订阅 2026-02-20
     6. **A 股定增终止**（2024-12-19 终止 2023 年度向特定对象发行 A 股股票事项）—— 腾讯新闻 2024-12
     7. **HR 招聘欺诈 + 劳动仲裁纠纷**（"我被 HR 骗进去"+ "仲裁委和法院与公司勾结"）—— 牛客网 + 知乎多年累积
   - **根因**：cron 流程的 `jisilu list --json` + `analyze` + A 股年报查询三件套只覆盖：
     - 招股期 / 价格 / 入场费 / 总股本 / 募资 / 市值 / 保荐人

     - A 股年报财务数字（营收 / 净利 / 毛利率 / 现金流）

     - 证监会备案质询（PITFALL #26）
     **不覆盖**：
     - 历年累计亏损（要拉 8 年财报）
     - 招投标违规 / 围标串标（要查行业监管新闻）

   - **2026-09-16 实证 cron 工具调用预算 ~28 次**（06700 + 09856 + 06727 三标的全 5 类 web_search × 3 + 招股 + 孖展 + 写报告 × 3 + push × 3），仍 ≤ 30 次预算；下次同批次可保持该预算，不需额外扩充。
    - **症状**：RSS relay 把当日 / 近期内已推送过的 title 视为 duplicate；本批内第 2 / 第 3 只如果 title 字符串与历史推送命中（哪怕只是同一天不同标的的 title），就会去重拒绝。
    - **根因猜测**：`scripts/push_rss.py` 内部调用 RSS relay 时，relay 端按 title 做模糊 / 精确 dedupe key；同一 relay 在短时间内收到多条 title 时，可能把日期 + 公司名 + 评分格式相近的条目误判为重复（实测同一 cron 批次 3 只，仅第 1 只成功，后 2 只 duplicate）。
    - **应对**：
      1. **必须每次都显式传 `--allow-duplicate`**：cron 推送命令模板改为 `python3 scripts/push_rss.py <md> --title "..." --endpoint <url> --source hk-ipo-research --insecure --allow-duplicate`（已在 PITFALL #10 的工具调用预算 + 此 PITFALL 双重保险）
      2. **验证 `--allow-duplicate` 真有效**：返回 `{"pushed": true, "response": {"id": "...", ...}}` 即真推送成功；不要把 `duplicate: true` 当成"已经推过了"的正面信号
      3. **不要因为首只成功就以为流程 OK**：每只都要看 `pushed == true`，否则该只新股实际未到达 RSS 订阅者
      4. **cron 任务结束后务必复查** `~/.hermes/cron/output/hk-ipo-daily-*.md` 文件数 vs RSS 返回 `pushed: true` 计数；不一致则补推
    - **历史验证**：2026-09-15 推送同一批次 3 只新股时，06700 `pushed: true`（RSS ID `20260915-083312-80b1aa`）、09856 `pushed: false, duplicate: true`（需加 `--allow-duplicate` 才能真推）、06727 `pushed: false, duplicate: true`（同上）。**教训**：cron 默认调用模板必须加 `--allow-duplicate`，否则 N ≥ 2 的批次会丢报告。
    - **2026-09-16 同批次 3 只新股验证 `--allow-duplicate` 有效**：06700 四方精创 / 09856 纳真科技 / 06727 星环科技——3 只均加 `--allow-duplicate` 推送，**全部 `pushed: true`**（RSS IDs `20260916-083202-ae1260` / `20260916-083204-893cfa` / `20260916-083206-4d3f18`），无 `duplicate: true` 误判。**结论**：cron 推送命令模板**强制固定**为 `python3 scripts/push_rss.py <md> --title "..." --endpoint <url> --source hk-ipo-research --insecure --allow-duplicate`，删掉 `--allow-duplicate` 会再次导致 N ≥ 2 批次丢报告。

## 研究流程

1. 标准化股票代码为五位数字，并确认公司名称、招股期、截止时间、发行价区间、每手股数、入场费和上市日。
2. 运行最贴近问题的本地命令，保存原始输出。财务及股权基本面必须另行阅读 [references/financial-research.md](references/financial-research.md) 和 [references/ownership-research.md](references/ownership-research.md) 并执行实时全网搜索；网络失败时切换独立站点，不回退到 HKEX PDF。
3. 对招股窗口、价格、孖展/超购倍数、基石、保荐人和已发生的价格表现尽量使用两个独立来源核验。数据源优先级和限制见 `references/data-sources.md`。
4. 给每个关键字段标注 `已核验`、`单一来源`、`来源冲突` 或 `未找到`。冲突时同时列出数值、时间戳和来源口径，不擅自平均。
5. 只有在数据足够时才按 `references/scoring.md` 计算 0–100 分。缺失项降低数据置信度；不要把缺失值当 0 分，也不要编造。
6. 把事实、推断和观点分开。任何“热门”“稳”“破发风险低”等判断都必须紧邻依据。

## 默认报告格式

1. 一句话结论：数据时点、有效候选数量、优先关注对象。
2. 排名表：代码/名称、招股窗口、发行价/入场费、孖展金额或倍数、券商覆盖、基石、评级、保荐人战绩、评分、数据置信度。
3. 单股详情：利好、风险、估值/AH、孖展总额及变化、基石质量、评级分歧、保荐人历史。
4. 排除项：已截止、仅上市、代码或日期易混淆的股票。
5. 来源：可点击链接、抓取时间和冲突说明。
6. 风险提示：第三方数据可能延迟或口径不同，不构成认购或买卖建议。

只有用户要求复盘时，才追加暗盘、开盘和首日收盘表现。结果尚未发生时写 `尚未发生`，不要输出空白结果表。

## 失败与合规

- 遇到 403、验证码、限流或页面改版时，记录失败源并切换脚本已有的备用源；不要绕过访问控制。
- 尊重网站条款和抓取频率；优先使用公开 API、港交所披露易和券商公开页面。
- 不执行认购、交易、登录或资金操作。
- 不声称数据“实时”却省略时间戳；不把预测超购倍数写成最终公开认购倍数。
