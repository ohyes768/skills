## 新增 PITFALLS

### PITFALL #30 — `push_rss.py` 按 title 字符串去重，cron 批次内第 2-N 只可能命中 `duplicate: true`

**触发场景（2026-09-15）**：cron 推送同一批次 3 只新股时，第一只 06700 推送成功 `{"pushed": true, "response": {"id": "20260915-083312-80b1aa", ...}}`；第二只 09856 立即返回 `{"pushed": false, "duplicate": true, "title": "2026-09-15 港股打新｜纳真科技（09856.HK）｜62分 B"}`；第三只 06727 同样 `{"pushed": false, "duplicate": true, "title": "..."}`。

**根因猜测**：`scripts/push_rss.py` 内部调用 RSS relay 时，relay 端按 title 做模糊 / 精确 dedupe key；同一 relay 在短时间内收到多条 title 时，可能把日期 + 公司名 + 评分格式相近的条目误判为重复（实测同一 cron 批次 3 只，仅第 1 只成功，后 2 只 duplicate）。**可能的次级原因**：RSS relay 端对同一日期下的多条标题启用滑动窗口去重，避免短时间内重复推送同一标的；当前实现误把"同日不同标的"也归类为重复。

**症状**：RSS 返回 `pushed: false, duplicate: true`，但本地 `.md` 文件已成功写入；cron agent 容易误以为"已经推过了"而漏掉对第 2-N 只的真正推送。

**应对**：
1. **必须每次都显式传 `--allow-duplicate`**：cron 推送命令模板改为
   ```bash
   python3 scripts/push_rss.py <md> \
     --title "YYYY-MM-DD 港股打新｜公司名（00000.HK）｜66分 B" \
     --endpoint https://web.duomi77.cn:9443/rss/api/rss-relay/post \
     --source hk-ipo-research --insecure --allow-duplicate
   ```
2. **验证 `--allow-duplicate` 真有效**：返回 `{"pushed": true, "response": {"id": "...", ...}}` 即真推送成功；不要把 `duplicate: true` 当成"已经推过了"的正面信号。
3. **不要因为首只成功就以为流程 OK**：每只都要看 `pushed == true`，否则该只新股实际未到达 RSS 订阅者。
4. **cron 任务结束后务必复查** `~/.hermes/cron/output/hk-ipo-daily-*.md` 文件数 vs RSS 返回 `pushed: true` 计数；不一致则补推。
5. **可选优化**：把 `--allow-duplicate` 写进 `scripts/push_rss.py` 默认行为（cron 场景天然就是"每日新批"，应天然不去重）；但需确认是否影响手动重复推送的语义。

**历史验证**：2026-09-15 推送同一批次 3 只新股时，06700 `pushed: true`（RSS ID `20260915-083312-80b1aa`）、09856 / 06727 默认参数下 `pushed: false, duplicate: true`；加 `--allow-duplicate` 后 09856 `pushed: true`（RSS ID `20260915-083318-9d6366`）、06727 `pushed: true`（RSS ID `20260915-083322-f68cd1`）。**教训**：cron 默认调用模板必须加 `--allow-duplicate`，否则 N ≥ 2 的批次会丢报告。
